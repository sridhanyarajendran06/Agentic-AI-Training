# Day 6 – Robust Tool Calling, Validation and Structured Outputs

## Objective

The objective of Day 6 was to make an AI agent more reliable and safer when working with tools. The implementation focused on validating tool arguments, enforcing structured outputs, handling tool failures without crashing, and preventing unsafe or repeated tool calls.

## 1. Tool Argument Validation

The `validate.py` program validates arguments generated by the model before passing them to a tool.

The validation checks include:

- Missing required arguments
- Incorrect argument types
- Invalid enum values
- Unexpected extra arguments

For example, `get_course_fee` requires a string `course_code` and optionally accepts `semester` with the values `odd` or `even`.

Invalid arguments are rejected before the actual tool is executed.

## 2. Stricter Tool Schemas

The `tools_v2.py` file defines two tools:

- `get_course_fee`
- `calculator`

Both tools have explicit JSON schemas. The schemas specify the expected argument names, data types, required fields, and whether additional arguments are allowed.

The calculator was also implemented using Python's AST module instead of unrestricted `eval()`. It only supports basic arithmetic operations such as addition, subtraction, multiplication, division, and unary minus.

This makes the calculator safer because unsupported expressions are rejected.

## 3. Structured Outputs

The `structured_demo.py` program compares three approaches:

1. Free-text output
2. JSON mode
3. Strict JSON Schema mode

In free-text mode, the model was able to return information in a JSON-like format, but the exact structure was not enforced.

In JSON mode, the model returned valid JSON, but the shape could still vary.

In strict schema mode, the response followed the predefined structure containing:

- `course_code`
- `wants_scholarship`
- `needs_tool`

This demonstrates that structured outputs make model responses more predictable for programs that need to process them.

## 4. Fault Injection

The `inject_faults.py` program was used to test whether the defensive guards work correctly.

The test cases included:

- A valid tool call
- Invalid JSON
- Unknown tool
- Missing required argument
- Wrong argument type
- Invalid enum value
- Invented extra argument
- Unknown course code
- Unsafe calculator expression
- Empty arguments

All test cases returned a string result or error message.

Nothing raised an unhandled exception and nothing crashed.

This demonstrates that tool failures can be converted into messages that the model can understand and potentially recover from.

## 5. Robust Agent

The `robust_agent.py` program combines the validation, tool execution and safety mechanisms into an agent loop.

The agent was tested with four questions.

**What is the total fee for CS101 and AI202 after a 10% scholarship?**

get_course_fee(AI202) -> 18000
